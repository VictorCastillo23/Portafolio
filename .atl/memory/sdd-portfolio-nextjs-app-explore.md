### Approaches

**A. GitHub data: build-time `fetch()` with Next.js caching directives**
- Pros: no extra tooling/script; leverages ISR (`next: { revalidate: N }`) for periodic auto-refresh without redeploy; idiomatic App Router pattern.
- Cons: unauthenticated GitHub REST rate limit is 60 req/hr per IP — real risk on Vercel if the default cache is not explicitly set. **Confirmed via research**: Next.js 14 defaulted `fetch` to `cache: 'force-cache'`, but Next.js 15 flipped the default to `cache: 'no-store'`. Since `prompt.md` says "14+" and it's currently Sept 2026 (Next 16 already exists per the CV's own Es Vitrina stack line), `create-next-app@latest` will almost certainly scaffold Next 15/16 — meaning every server render would hit GitHub live unless caching is set explicitly. Silent runtime rate-limit exposure if this is missed.
- Effort: Low-Medium (mostly one caching-config decision, but easy to get wrong silently).

**B. Cached JSON, generated by a script (checked in or run in CI/prebuild)**
- Pros: zero runtime API calls, zero rate-limit risk, fully deterministic builds, compatible even with static export if that's ever wanted, sidesteps the Next 14→15 fetch-default trap entirely, matches the "no backend" simplicity intent.
- Cons: data goes stale until someone reruns the script and redeploys; needs a small `scripts/fetch-github.ts` + npm script.
- Effort: Low.

### Recommendation
**Cached JSON (Approach B)** as the default, generated by a small script and committed (or run as an explicit `prebuild`/manual step before deploy) — this is a low-traffic personal portfolio where the project list changes rarely, and avoiding the GitHub rate-limit/caching-default trap outweighs live freshness. If auto-freshness is later desired, layer in `next: { revalidate: 86400 }` (daily ISR) as a middle ground — but start with the simpler, deterministic option. Regardless of which is chosen, the 5-repo (soon to be reconciled to account for `omegaup`) allow-list must be a hardcoded curation config in `data/projects.ts`, joined by repo name against whichever data source is used — never derived from a "pinned" API field, because that field does not exist in the REST response.

Content split: `data/content.ts` (pure hardcoded CV content) is a distinct concern from `data/projects.ts` (curation/allow-list + manual overrides) and the GitHub data source itself (`lib/github.ts` fetch or `data/github-repos.json`) — three layers, merged at render/build time by repo name, so human-authored judgment (which repos, what description) never gets silently overwritten by an API refresh.

### Risks
- GitHub REST API has no pinned-repo field — must not be treated as a dynamic filter; requires a hardcoded allow-list (already identified above).
- Next.js 15's default fetch-caching flip (`no-store` vs 14's `force-cache`) creates a silent rate-limit/latency risk if a build-time-fetch approach is chosen without an explicit cache/revalidate directive — mitigated by recommending cached-JSON.
- Unauthenticated GitHub API rate limit (60 req/hr/IP) is a real constraint on Vercel if any runtime (non-build-time) fetching path is used.
- 4 of 5 named repos lack GitHub descriptions — content blocker for Projects section until user supplies/approves copy.
- `omegaup` repo exists on the account but isn't in the named list — needs explicit user confirmation to exclude, otherwise a naive "fetch all repos" implementation would wrongly include it.
- Minor content discrepancy: Risk-Game description language differs between `prompt.md` (Next.js) and live GitHub (C#) — needs user clarification, should not be silently resolved either way.
- "Strict TDD Mode: enabled" is set at the orchestrator level; a static-content portfolio has limited testable logic — the two genuinely unit-testable pieces are the GitHub-data merge/curation logic (`lib/github.ts`/`data/projects.ts` join) and the scroll-spy hook.
